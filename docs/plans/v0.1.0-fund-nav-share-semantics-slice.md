# v0.1.0 Slice 8 — Fund NAV and Share Semantic Hardening

Status: **READY_FOR_EXECUTION**

Parent plan: [`v0.1.0-pit-market-facts.md`](v0.1.0-pit-market-facts.md)

## Objective

Harden the existing typed `fund_nav` and `fund_share` transports where the
current funmoney consumer exposes concrete M3 dependencies. The slice validates
request and response scope, provider calendar dates, truncation boundaries, and
provider-native revision/missing-value behavior without moving premium,
availability-session, or share-unit calculations into OMD.

## Evidence and Provider Contract

The current consumer calls `fund_nav` per `ts_code` and date range, requires
`ts_code`, `ann_date`, `nav_date`, and `unit_nav`, and performs the as-of premium
join itself. It calls `fund_share` per `ts_code` and date windows, preserving
`fd_share` as a provider-native value before applying a consumer-owned one-trade-
day lag. These dependencies are visible in:

- `/Users/ron/Documents/funmoney_backtest/data_pipeline/etf_premium.py`;
- `/Users/ron/Documents/funmoney_backtest/data_pipeline/etf_iter04_contract.py`.

The official Tushare contracts are:

- `fund_nav`: <https://tushare.pro/document/2?doc_id=119>;
- `fund_share`: <https://tushare.pro/document/2?doc_id=207>.

The official `fund_share` contract states a 2000-row per-call limit and that
`fd_share` is expressed in ten-thousand shares (万份). The official `fund_nav`
page does not state a row cap, so OMD must not invent one.

## Request Contract

`FundNavRequest` must:

- require exactly one non-empty `ts_code` or `nav_date` selector;
- allow a start/end range only with `ts_code`;
- validate `nav_date`, `start_date`, and `end_date` as real `YYYYMMDD` calendar
  dates and reject reversed ranges;
- preserve `market` as a provider-native optional filter without inventing a
  stricter enum that would break existing callers;
- preserve the existing default fields and explicit field selection.

`FundShareRequest` must:

- require at least one non-empty `ts_code`, `trade_date`, or `market` filter;
- allow a start/end range only with `ts_code`;
- validate `trade_date`, `start_date`, and `end_date` as real `YYYYMMDD`
  calendar dates and reject reversed ranges;
- preserve comma-separated provider-native `ts_code` selectors and optional
  `market` values rather than normalizing or interpreting them in core;
- preserve the existing default fields and explicit field selection.

This slice must not change the global `_date` behavior used by unrelated
accepted endpoints. Add or use validation narrowly for these two request
classes.

## Response Scope and Date Contract

For non-empty `fund_nav` responses:

- every `ts_code` and `nav_date` key remains required and non-null;
- `ann_date` remains a required non-null key because the current premium/PIT
  caller requires explicit announcement-date evidence; callers that do not
  request it cannot construct that M3 fact;
- every `nav_date` and `ann_date` must be a real string `YYYYMMDD` date;
- a `ts_code` request rejects rows for any other symbol;
- a `nav_date` request rejects rows for any other NAV date;
- a ranged `ts_code` request rejects NAV dates outside its inclusive range;
- repeated `(ts_code, nav_date, ann_date)` rows are preserved as provider-native
  observations/revisions, including exact duplicates;
- value fields such as `unit_nav`, `accum_nav`, `net_asset`, and
  `total_netasset` preserve provider-native null, zero, NaN, and infinities;
- stable sorting remains `ts_code`, then `nav_date`, then `ann_date`;
- no undocumented row cap is added.

For non-empty `fund_share` responses:

- `ts_code` and `trade_date` remain required and non-null;
- every `trade_date` must be a real string `YYYYMMDD` date;
- a `ts_code` request accepts only symbols named by the comma-separated
  selector and rejects all others;
- a `trade_date` request rejects rows for any other trade date;
- a ranged `ts_code` request rejects dates outside its inclusive range;
- `(ts_code, trade_date)` remains unique and output sorting remains stable;
- 1999 rows are accepted and exactly 2000 rows fail with `PaginationError` as
  an ambiguous truncated response;
- `fd_share` remains provider-native in ten-thousand shares, including null,
  zero, NaN, and infinities. No silent scaling is allowed.

Empty responses continue to follow the request's existing `EmptyPolicy`.

## Availability and Consumer Boundary

`ann_date` and `trade_date` are provider-native dates, not timestamps. Their
presence alone does not prove intraday availability or a consumer session.
Offline evidence must show:

- a `fund_nav` row using `ann_date` as source evidence has date precision and
  remains `PIT_UNPROVEN`;
- a missing announcement timestamp is not invented from `nav_date`;
- an old `nav_date` in a currently fetched response does not prove historical
  vintage;
- row revisions require explicit same-key `RawFactEnvelope.classify_against`
  evidence.

The consumer continues to own next-trading-day lag, cutoff policy, premium
calculation, ETF/QDII eligibility, `first_usable_session`, storage, and
publication. OMD does not turn `fd_share` into market value or infer an
announcement timestamp.

## Non-goals and Stop Conditions

Do not:

- add pagination to `fund_nav` without an official cap/window contract;
- drop, deduplicate, fill, or coerce provider-native NAV/share values;
- infer an availability timestamp, next session, premium, ETF eligibility, or
  adjusted NAV policy;
- change consumer code, dependencies, versions, snapshots, or accepted endpoint
  behavior outside these two transports;
- commit, push, publish, or call a live provider.

Stop with `EXECUTION_BLOCKED` if official semantics conflict with this frozen
contract, correct scope validation requires changing a consumer-owned policy,
the contract hash changes, or overlapping changes cannot be preserved.
