# v0.1.1 — ETF PCF Endpoint and Windowed Retrieval Plan

Status: **ACCEPTED — 2026-08-03**

Target release: `0.1.1`

Parent plan: [`v0.1.0-pit-market-facts.md`](v0.1.0-pit-market-facts.md)

## Objective

Add typed, fail-closed support for Tushare `etf_sh_cons` and `etf_sz_cons`,
plus a deterministic windowed PCF retrieval recipe that owns the provider's
3000-row truncation boundary. Preserve each exchange's provider-native fields,
values, dates, and provenance. Do not move consumer universe, point-in-time lag,
feature construction, storage, or strategy policy into OMD.

This is a provider transport and retrieval slice. A PCF row is an observed ETF
creation/redemption basket component, not investor cash-flow evidence.

## Public API Contract

Add and publicly export:

- `EtfShConsRequest`;
- `EtfSzConsRequest`;
- `EtfPcfHistoryRequest`;
- `EtfPcfHistoryResult`;
- `TushareClient.fetch_etf_sh_cons(request)`;
- `TushareClient.fetch_etf_sz_cons(request)`;
- `fetch_etf_pcf_history(client, request)` from a focused recipe module.

Keep endpoint request classes separate even where their selectors overlap. The
raw endpoint results must not be coerced into a false unified exchange schema.

`EtfPcfHistoryRequest` must require exactly one non-empty `ts_code`, an explicit
`exchange` of `SH` or `SZ`, and a bounded inclusive `start_date`/`end_date`.
It must reject an exchange that conflicts with the ETF code suffix. The recipe
routes to the corresponding typed endpoint and returns one provider-native
result table; it does not add a synthetic availability timestamp or normalized
consumer columns.

The history request must also require an explicit `EmptyPolicy` and may accept
explicit fields. It delegates field/key validation to the selected exchange
endpoint request and must not silently replace an empty policy or field list.

`EtfPcfHistoryResult` must defensively expose the combined provider-native
Pandas frame, the successful leaf-window `FetchProvenance` objects in
deterministic request order, the total provider request count, and the number
of exact-3000 truncation responses that caused bisection. A truncation response
is not a successful complete result and therefore must not be represented as a
fabricated successful provenance object. The counts make those calls
inspectable without exposing or accepting their incomplete rows. Empty allowed
history has one successful leaf provenance, zero rows, one total request, and
zero truncations; `EmptyPolicy.ERROR` propagates `EmptyResponseError`.

## Endpoint Request Contract

Both endpoint requests may accept the provider-native selectors:

- `ts_code`;
- `trade_date`;
- `con_code`;
- `start_date` and `end_date`;
- explicit `fields` and the existing `EmptyPolicy`.

Validation must:

- require at least one non-empty selector from `ts_code`, `trade_date`,
  `con_code`, or a complete date range;
- allow a date range only when both boundaries are present;
- validate all dates as real `YYYYMMDD` calendar dates and reject reversed
  ranges;
- reject `.SZ` ETF selectors on `EtfShConsRequest` and `.SH` selectors on
  `EtfSzConsRequest`;
- preserve provider-native component codes, including non-mainland suffixes;
- send only documented provider parameters and exact requested fields.

Default Shanghai fields, in provider order:

```text
trade_date,ts_code,con_code,con_name,qty,sub_flag,cpr,rdr,sca,exchange
```

Default Shenzhen fields, in provider order:

```text
trade_date,ts_code,con_code,con_name,qty,sub_flag,cpr,rdr,sub_cc,red_cc,exchange
```

Do not add `sca` to Shenzhen responses or `sub_cc`/`red_cc` to Shanghai
responses. A consumer may explicitly normalize the union after retrieval.

## Response and Value Semantics

For every non-empty response:

- `trade_date`, `ts_code`, and `con_code` are required, non-null keys;
- dates must be real string `YYYYMMDD` values;
- response rows must satisfy every supplied symbol, component, exact-date, and
  inclusive-range selector;
- stable output ordering is `ts_code`, `trade_date`, then `con_code`;
- rows and duplicate observations are preserved; OMD must not silently choose
  a revision or deduplicate a key;
- `qty` is documented in shares;
- `cpr` and `rdr` are documented as percentages;
- `sca`, `sub_cc`, and `red_cc` are documented in CNY;
- null, zero, NaN, infinity, and provider sentinels such as `-` remain
  provider-native. OMD must not silently coerce, fill, scale, or reinterpret
  them.

The two endpoints use different cash-replacement semantics:

- Shanghai `sca`: replacement amount;
- Shenzhen `sub_cc`: subscription replacement amount;
- Shenzhen `red_cc`: redemption replacement amount.

Names, cash-substitution flags, and exchange codes remain raw provider values.
OMD must not translate Chinese flag labels or invent an enum until the provider
publishes a complete stable domain and a consumer requires it.

## Truncation and Windowed Retrieval

Each single-call endpoint method must fail with `PaginationError` when the
provider returns exactly 3000 rows. A full-sized page is ambiguous and must not
be accepted as complete. Responses of 2999 rows are accepted.

`fetch_etf_pcf_history` must own deterministic recovery from that boundary:

1. request the full inclusive date range for one ETF;
2. accept a response below 3000 rows;
3. on `PaginationError`, bisect the calendar-date range at its midpoint and
   retrieve the two non-overlapping inclusive halves;
4. concatenate without deduplication, then apply the stable raw ordering;
5. if a single calendar day still reaches 3000 rows, fail with
   `PaginationError` rather than returning an ambiguous result.

Do not use offset pagination: the official endpoint documents code/date
looping, not stable offsets. Do not assume that five calendar days is universally
safe; that value belongs only to the current consumer implementation.

## Availability, Revision, and Ownership Boundary

The provider describes PCF as daily pre-market disclosure but supplies only a
date. Therefore:

- `trade_date` is provider date evidence, not an intraday timestamp;
- a newly fetched old row does not prove its historical vintage;
- a row remains `PIT_UNPROVEN` unless a captured raw-fact envelope or equivalent
  snapshot proves observation time;
- OMD may attach standard request/response provenance, but must not invent a
  market-session availability time;
- revision classification requires explicit same-key snapshot evidence.

The consumer continues to own:

- ETF universe and exchange selection policy;
- trading-calendar lag and `available_date`/`available_at`;
- PCF panel normalization and optional cross-exchange union;
- duplicate-collapse policy for a published dataset;
- cash-flow, substitution, breadth, or other feature definitions;
- storage paths, dataset fingerprints, strategy use, and promotion decisions.

Broker, live execution, and strategy code are outside this slice.

## Non-goals and Stop Conditions

Do not:

- call PCF observed investor subscriptions, redemptions, or net cash flow;
- merge exchange-specific cash fields into a synthetic common value;
- infer availability timestamps, next sessions, revisions, or historical
  vintages;
- add consumer feature, strategy, universe, storage, or broker logic;
- accept a 3000-row response as complete;
- make live provider calls, commit, push, or publish without separate authority.

Stop with `EXECUTION_BLOCKED` if official fields/units/caps conflict with this
contract, a one-day response still reaches 3000 rows, correct behavior requires
consumer policy, package-version ownership is unclear, or overlapping dirty
changes cannot be preserved.

## Acceptance

Accept only after independent review of the public request and client API,
exchange-specific schemas, cap boundaries, recursive range coverage, native
value preservation, PIT limitations, complete offline validation, and built
artifacts. Successful command exits alone are insufficient.
