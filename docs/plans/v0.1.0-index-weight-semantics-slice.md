# v0.1.0 Slice 5 — Index Weight Semantic Hardening

Status: **READY_FOR_EXECUTION**

Parent plan: [`v0.1.0-pit-market-facts.md`](v0.1.0-pit-market-facts.md)

## Objective

Harden the existing typed Tushare `index_weight` transport contract so an
accepted response is demonstrably within the caller's requested index and date
scope. Preserve provider-native monthly weight observations without inventing
an effective period, availability timestamp, constituent fill, or weight
normalization rule.

Official provider reference reviewed on 2026-08-02:

- <https://tushare.pro/document/2?doc_id=96> (`index_weight`)

Concrete callers in `funmoney_backtest` consume the raw fields
`index_code`, `con_code`, `trade_date`, and `weight`, then separately own
percent-to-decimal conversion, trading-session alignment, snapshot storage,
and selection of a historical weight observation. Those consumer policies are
not moved into OMD by this slice.

## Public API

The public API remains:

```python
IndexWeightRequest
TushareClient.fetch_index_weight(request)
```

No new result type, recipe, or availability field is added.

## Request Contract

Every request requires:

- an explicit `EmptyPolicy`;
- one non-empty `index_code`, forwarded unchanged; and
- exactly one complete date orientation:
  1. one exact `trade_date`; or
  2. both `start_date` and `end_date`, inclusive, within one calendar month.

All dates use `YYYYMMDD`. A missing selector, partial range, exact date mixed
with either range boundary, malformed date, reversed range, cross-month range,
or whitespace-only index code fails before provider invocation.

The one-calendar-month range is an OMD fail-closed request bound based on the
provider's monthly-data description and recommendation to query the first and
last day of one month. It is not a claim that a wider provider query is
invalid. Consumers needing longer history must issue explicit monthly
requests so request identities and empty/coverage failures remain inspectable.

Default fields, in provider order:

```text
index_code
con_code
trade_date
weight
```

Custom fields remain ordered, non-empty, and duplicate-free, but all three
identity fields `index_code`, `con_code`, and `trade_date` must be requested.

## Provider-Native Semantics

- `index_code` identifies the provider index.
- `con_code` identifies the provider constituent.
- `trade_date` is the date attached to the monthly provider observation. It
  is neither a proven publication time nor a universal effective-from or
  effective-through boundary.
- `weight` is the provider-native percentage value, not a decimal ratio.
- null or non-finite `weight` remains missing/non-finite; OMD does not turn it
  into zero or reject it merely because it is not finite.
- OMD does not require weights to sum to 100, renormalize partial coverage,
  fill absent constituents, or infer additions/removals.

## Response, Identity, and Revision Contract

For every non-empty response:

- requested fields must all be present;
- `index_code`, `con_code`, and `trade_date` must be non-null;
- every `index_code` must equal the requested `index_code` exactly;
- an exact-date response may contain only that `trade_date`;
- a range response may contain only dates within the inclusive requested
  bounds;
- rows are sorted by `index_code`, then `trade_date`, then `con_code`;
- `(index_code, trade_date, con_code)` is unique within one response;
- an in-response duplicate identity raises `SchemaMismatchError` even when
  weight values differ; no last-write-wins rule is invented;
- cross-fetch changes are revisions and remain distinguishable through
  immutable snapshot payload versions and observation records;
- no undocumented row cap is invented from this provider page.

Out-of-scope index codes or dates raise `SchemaMismatchError`; they are a
deterministic provider-response contract mismatch, not an empty result.
Malformed/non-DataFrame responses use the existing schema error. Empty results
continue to follow `EmptyPolicy`. Retry, authentication, permission,
rate-limit, provenance, defensive-copy, and credential behavior are unchanged.

## Availability Boundary

The provider describes monthly data and its public source, but does not provide
a precise publication timestamp or a universal next-session applicability
rule. Therefore this endpoint transport:

- does not map `trade_date` to `source_available_at`;
- does not infer `first_usable_session`;
- does not claim a current response is a historical vintage;
- does not attach an effective interval to a constituent weight;
- retains `retrieved_at` only as current fetch provenance;
- relies on separately persisted snapshot observations for exact-payload
  first-observed evidence when the caller chooses to store them.

Any consumer rule such as “use on the next canonical session” must remain an
explicit consumer-owned transform with its own evidence and tests.
