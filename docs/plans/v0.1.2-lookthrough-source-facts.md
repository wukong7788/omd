## 1. Objective

Deliver the smallest OMD release that can capture, replay, and validate the
provider-native source facts needed by an ETF look-through audit:

1. observed ETF-to-index mappings from `etf_basic`;
2. exact-date index constituent-weight vintages from `index_weight`;
3. stock identity and industry-membership facts from `stock_basic` and
   `index_member_all`;
4. immutable snapshot, request, response, observation, availability, revision,
   and retrieval-completeness evidence for those facts.

The release must improve the evidence boundary without claiming that currently
retrieved data existed historically. It is acceptable, and expected, for the
consumer audit to remain blocked when historical mapping vintages, an auditable
constituent-count authority, or consumer-owned classifications are unavailable.

This release is provider infrastructure. It must not contain ETF selection,
portfolio exposure, strategy, backtest, signal, live execution, or promotion
logic.

## 2. Current-state evidence

OMD `0.1.1` already provides:

- typed `EtfBasicRequest` and `IndexWeightRequest`;
- provider-native `TushareFetchResult` and `FetchProvenance`;
- append-only `SnapshotStore` observations and replay validation;
- `AvailabilityEvidence` and `RawFactEnvelope`;
- explicit Pandas/Polars representation adapters;
- typed ETF PCF endpoints and deterministic bounded retrieval.

The missing OMD capabilities are:

- no typed `stock_basic` endpoint;
- no typed `index_member_all` endpoint for dated industry membership;
- no public deterministic typed-result-to-snapshot serialization/capture path;
- no endpoint-specific export of observed ETF mapping facts;
- no index-weight vintage audit result that distinguishes retrieval completeness,
  weight-total quality, and economically complete membership;
- no look-through source-fact bundle that reports unsupported index codes and
  unavailable classifications without filling them.

The consumer currently has 26 held ETF symbols over 196 decision dates. Its local
data contains only current-style ETF mappings, index weights without snapshot or
availability identity, and stock prices without the required classification facts.
OMD must not retrofit these current observations into historical dates.

## 4. Ownership boundary

## 5. Public API slices

### 5.1 Deterministic observed-result capture

Add a narrow Tushare observation module that can capture an already validated
`TushareFetchResult` into a caller-provided `SnapshotStore`:

```python
capture_tushare_result(
    store: SnapshotStore,
    request: SupportedTushareRequest,
    result: TushareFetchResult,
    *,
    observed_at: datetime,
) -> TushareObservedResult
```

`TushareObservedResult` must defensively expose:

- the provider-native frame;
- `FetchProvenance`;
- `SnapshotObservationRef`;
- `AvailabilityEvidence`;
- deterministic serialization identifier;
- request, response, snapshot, observation and fact-version identities;
- row count, ordered columns and a canonical content hash.

The capture path must:

- require an aware explicit `observed_at`; no wall-clock default;
- use `SnapshotMode.APPEND`;
- serialize the provider-native frame deterministically, including column order,
  dtype identity, null, NaN, infinity, date strings and row order;
- validate replay before returning;
- preserve unchanged observations and revised payloads as distinct observation
  history without overwriting;
- never read credentials or call a provider;
- reject a result whose provenance/request identity does not match the request.

Do not create a universal dataframe snapshot format outside the Tushare adapter in
this release. The format identifier and schema version must be explicit so later
versions can coexist.

### 5.2 `StockBasicRequest`

Add and export:

- `StockBasicRequest`;
- `TushareClient.fetch_stock_basic(request)`.

Freeze provider-native selectors and fields from the official contract. The default
identity fields must include at least `ts_code`, `symbol`, `name`, `market`,
`exchange`, `list_status`, `list_date` and `delist_date`; `industry` is optional
metadata, not identity.

Requirements:

- selectors are explicit and nonblank;
- a broad all-market request requires an explicit opt-in rather than an accidental
  empty request;
- exact requested fields and provider-native strings are preserved;
- `ts_code` is required and non-null for non-empty results;
- duplicate `ts_code` rows fail closed for one declared `list_status` snapshot;
- a response at the documented maximum row count is ambiguous and raises
  `PaginationError` unless the reviewed provider contract supplies a proven paging
  mechanism;
- current `industry` is marked current-observation metadata and never gains an
  inferred historical effective interval.

### 5.3 `IndexMemberAllRequest`

Add and export:

- `IndexMemberAllRequest`;
- `TushareClient.fetch_index_member_all(request)`.

Supported selectors must match the official endpoint: `l1_code`, `l2_code`,
`l3_code`, `ts_code` and explicit `is_new`. At least one classification or stock
selector is required. Broad implicit full-market requests are forbidden.

The default fields must preserve:

```text
l1_code,l1_name,l2_code,l2_name,l3_code,l3_name,
ts_code,name,in_date,out_date,is_new
```

Validation must preserve null `out_date` as open-ended provider data, validate every
non-null date, reject rows outside supplied selectors, retain provider-native names,
and use stable ordering by `ts_code`, `in_date`, then industry codes. Duplicate exact
rows are preserved; conflicting duplicate membership identities fail closed rather
than being collapsed.

The endpoint's 2000-row maximum must be explicit. A response at that boundary raises
`PaginationError`. The first release may support complete history only for one
explicit `ts_code` per request; it must not pretend an unpageable broad query is
complete.

`in_date`/`out_date` establish provider-native membership intervals. They do not
prove when OMD or the provider first published that interval. Snapshot observation
evidence remains mandatory for PIT use.

### 5.4 ETF-to-index mapping observations

Add a pure recipe over captured `etf_basic` observations:

```python
build_etf_index_mapping_observations(
    observations: Sequence[TushareObservedResult],
) -> EtfIndexMappingObservationResult
```

The output grain is one observed exact mapping version per
`(etf_symbol, observation_identity)`. It must include:

```text
etf_symbol
index_code
list_status
provider_first_observed_at
snapshot_fetched_at
request_identity
response_sha256
snapshot_identity
observation_identity
fact_version
mapping_observation_status
quality_flags
```

Allowed statuses are:

- `CURRENT_OBSERVATION_ONLY`;
- `UNCHANGED_FROM_PREVIOUS`;
- `REVISED_FROM_PREVIOUS`;
- `MISSING_INDEX_CODE`.

The recipe must not emit `effective_date`, historical mapping intervals, or
`first_usable_session` unless a future provider endpoint supplies explicit evidence
and a new reviewed contract authorizes it. A newly observed old ETF record remains
`PIT_UNPROVEN` for earlier decision dates.

### 5.5 Index-weight vintage evidence

Add a pure recipe over one captured exact-date `index_weight` result:

```python
audit_index_weight_vintage(
    observation: TushareObservedResult,
    *,
    total_weight_tolerance: Decimal,
    expected_component_count: int | None = None,
    expected_count_basis: str | None = None,
) -> IndexWeightVintageEvidence
```

The result must preserve native percent weights and may additionally expose decimal
weights only under the explicit conversion identity
`percent_to_decimal_divide_100`. It must include:

- exact `index_code` and `trade_date`;
- native and decimal unit identities;
- observed distinct component count;
- optional caller-declared expected count and its nonblank basis;
- duplicate/null/non-finite/range diagnostics;
- native and decimal weight sums;
- tolerance and deterministic vintage identity;
- snapshot and observation lineage;
- retrieval and economic-completeness statuses.

Status semantics must remain separate:

- `RETRIEVAL_COMPLETE`: the endpoint contract proves the exact request was not
  truncated and all response validations passed;
- `RETRIEVAL_COMPLETENESS_UNPROVEN`: the official endpoint lacks a usable
  truncation/count guarantee;
- `WEIGHT_TOTAL_PASS` / `WEIGHT_TOTAL_FAIL`: arithmetic quality only;
- `EXPECTED_COUNT_MATCH` / `EXPECTED_COUNT_MISSING` / `EXPECTED_COUNT_MISMATCH`;
- `ECONOMIC_COMPLETENESS_UNPROVEN` unless both retrieval and an auditable expected
  count authority pass.

Observed row count must not silently become a source-declared expected count.
Weight sum near 100% is necessary but not sufficient for economic completeness.
Missing constituents are never treated as zero.

### 5.6 Look-through source-fact bundle

Add an immutable manifest-only bundle builder that combines explicit mapping,
weight and industry observations without computing portfolio exposure:

```python
build_lookthrough_source_bundle(
    mapping_observations: EtfIndexMappingObservationResult,
    weight_vintages: Sequence[IndexWeightVintageEvidence],
    industry_observations: Sequence[TushareObservedResult],
    *,
    output_dir: Path,
) -> LookthroughSourceBundle
```

The bundle must be new/empty-output only, bind every input identity and content hash,
and expose per ETF/index/component evidence statuses. Unsupported and missing index
codes remain explicit. The bundle must not:

- choose a consumer decision-date vintage;
- derive `first_usable_session`;
- fill missing industry with `UNKNOWN` in a success table;
- generate style, cluster, overlap or portfolio exposure;
- emit a strategy-ready universe or action.

The bundle's top-level readiness values are limited to:

- `SOURCE_FACTS_COMPLETE`;
- `SOURCE_FACTS_PARTIAL`;
- `CURRENT_OBSERVATION_ONLY`;
- `BLOCKED_UNPROVEN_COMPLETENESS`.

`SOURCE_FACTS_COMPLETE` means complete for the declared captured inputs, not
historically PIT-valid for a consumer decision date.

## 12. Release decision and downstream gate

OMD `0.1.2` is releasable when the SDK capabilities and offline evidence above pass,
even if the funmoney historical audit remains blocked. Release success means the
source-fact boundary is honest and reusable; it does not mean historical PIT coverage
exists.

After an immutable `0.1.2` release, funmoney may open a separate migration session to:

1. pin `ohmydata==0.1.2`;
2. capture only authorized new observations;
3. derive consumer-owned `first_usable_session` prospectively;
4. compare OMD source-fact bundles with the frozen look-through validator;
5. keep unsupported history, style and cluster gaps blocked;
6. rerun the canonical B6 no-drift matrix before accepting any consumer change.

Only a later, separately reviewed data source with real historical mapping and
availability evidence can unblock the full historical look-through audit.
