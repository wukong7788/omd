# v0.1.0 Slice 2 — Snapshot Observation and Exact-Payload Versioning

Status: **READY_FOR_EXECUTION**

Parent plan: [`v0.1.0-pit-market-facts.md`](v0.1.0-pit-market-facts.md)

## Objective

Extend the provider-independent snapshot core so callers can distinguish:

- the timestamp of the current fetch observation;
- the first time OMD successfully persisted one exact serialized payload;
- a stable exact-payload fact version;
- later observations of unchanged bytes from later revised payload versions.

The existing `SnapshotStore.write()` and `replay()` APIs, snapshot paths, and
manifest schema version 1 remain backward compatible. This slice adds an
append-only observation ledger rather than rewriting existing snapshots or
renaming the legacy manifest field.

This is storage/provenance infrastructure only. It does not infer source
publication time, endpoint event dates, consumer sessions, or historical PIT
availability.

## Existing Snapshot Semantics

For an immutable snapshot created by `SnapshotStore.write()`:

- `manifest["retrieved_at"]` is the timestamp supplied by the writer that won
  the atomic publication race;
- repeated same-request/same-bytes writes return the existing snapshot and do
  not replace that timestamp;
- different payload bytes in `APPEND` mode create a different immutable
  snapshot;
- `FROZEN` mode still rejects a different payload.

For availability-aware use, this slice gives the retained legacy
`retrieved_at` field the precise public interpretation:

> `provider_first_observed_at` is the timestamp when this SnapshotStore first
> successfully persisted the exact request + serialization + payload version.

It is not evidence that the provider published the value at that time, nor
that a consumer could use it at that time.

## Public API

Add and export from `ohmydata.core`:

```python
SnapshotObservationRef
SnapshotStore.observe(...)
SnapshotStore.observations(...)
SnapshotStore.provider_first_observed_at(...)
SnapshotStore.replay_observation(...)
SnapshotRef.fact_version
```

The existing methods and dataclass constructor fields remain unchanged.

### `SnapshotRef.fact_version`

`fact_version` is the lowercase SHA-256 of compact, sorted-key UTF-8 JSON with
`ensure_ascii=False` for exactly this object:

```json
{
  "request_identity": "<full request SHA-256>",
  "response_sha256": "<full payload SHA-256>",
  "serialization_identifier": "<validated serialization identifier>"
}
```

`SnapshotMode` is deliberately excluded: the same request, exact bytes, and
serialization represent the same fact version whether stored under APPEND or
FROZEN policy. A different request, payload, or serialization produces a
different fact version.

The existing `snapshot_identity` remains unchanged and continues to include
mode for snapshot storage identity and integrity.

### `SnapshotObservationRef`

The frozen public reference contains:

```text
path: Path
observation_identity: str
snapshot_identity: str
fact_version: str
mode: SnapshotMode
provider: str
endpoint: str
request_identity: str
response_sha256: str
serialization_identifier: str
snapshot_fetched_at: datetime
```

The timestamp is timezone-aware and normalized to UTC. The type contains no
payload, dataframe, provider-specific semantics, or free-form metadata.

## Observation Storage Contract

`SnapshotStore.observe(spec, payload, snapshot_fetched_at, serialization,
mode=APPEND)` must:

1. validate inputs using the existing snapshot rules;
2. call the existing immutable snapshot publication path;
3. validate the resulting snapshot;
4. reject `snapshot_fetched_at` earlier than that exact snapshot's retained
   `provider_first_observed_at` with `SnapshotIntegrityError` rather than
   backdating an observation;
5. atomically append an immutable observation manifest;
6. return a validated `SnapshotObservationRef`.

Observation path:

```text
<root>/<provider>/<endpoint>/<request_identity>/
  observations/<snapshot_identity>/<observation_identity>/observation.json
```

`observation_identity` is the lowercase SHA-256 of compact, sorted-key UTF-8
JSON with `ensure_ascii=False` for exactly:

```json
{
  "snapshot_fetched_at": "<UTC ISO-8601 with Z suffix>",
  "snapshot_identity": "<full snapshot SHA-256>"
}
```

Microseconds are preserved when non-zero and omitted when zero, matching
Python `datetime.isoformat()` followed by replacing `+00:00` with `Z`.
Repeating the same snapshot and exact timestamp is idempotent; the existing
observation is validated and returned. The same payload fetched at a later
timestamp creates a distinct observation without changing its fact version or
first-observed time.

Observation manifest schema version 1 contains exactly:

```text
observation_schema_version
provider
endpoint
request_identity
response_sha256
serialization_identifier
snapshot_identity
fact_version
mode
snapshot_fetched_at
observation_identity
```

The observation manifest does not duplicate the canonical request or payload.
Validation follows its linked snapshot and verifies every identity field,
timestamp, expected path, and exact key set.

Writes use a unique temporary directory under the final observation parent and
one atomic directory rename. They never overwrite a final observation. An
interruption may leave the already-valid content snapshot but must not leave a
valid-looking partial observation or another writer's temporary directory.

## Read and Replay Contract

`observations(snapshot_ref)`:

- validates the supplied snapshot ref first;
- returns all validated observation refs linked to it;
- sorts by `snapshot_fetched_at`, then `observation_identity`;
- returns an empty tuple for a legacy snapshot with no observation receipts;
- fails closed if an observation directory or manifest under that exact
  snapshot ledger is malformed, unexpected, or linked to another snapshot;
- returns a tuple and no mutable internal state.

`provider_first_observed_at(snapshot_ref)` validates the snapshot and returns
the retained manifest `retrieved_at` as a timezone-aware UTC `datetime`. It
works for both legacy `write()` snapshots and new `observe()` snapshots.

`replay_observation(observation_ref, expected=None)`:

- fully validates the observation and its linked snapshot;
- optionally validates the expected `RequestSpec` using the existing replay
  contract;
- returns the existing defensive `SnapshotReplay` exact bytes and snapshot
  manifest;
- never deserializes provider data.

## Concurrency and Revision Semantics

- Concurrent identical `observe()` calls with the same timestamp are
  idempotent.
- Concurrent observations with different timestamps may create distinct
  receipts for the same exact fact version.
- The atomic winner of a newly published exact payload establishes its
  retained first-observed timestamp. A racing caller with an earlier supplied
  timestamp must fail closed rather than rewrite the winner.
- A different exact payload under the same APPEND request creates a different
  `SnapshotRef.fact_version` and independent observation ledger.
- This infrastructure records versions; it does not decide whether a provider
  change is a correction, restatement, late arrival, or strategy-usable
  revision.

## Required Tests

All tests are offline and synthetic. Cover:

- `fact_version` determinism and change on request/payload/serialization, but
  not mode;
- legacy `write()`/`replay()` behavior and manifest schema remaining unchanged;
- first-observed time from legacy and observation-backed snapshots;
- one observation round trip and exact manifest/path inspection;
- same payload/same timestamp idempotency;
- same payload/later timestamp producing two ordered observations with one
  fact version and unchanged first-observed time;
- same request/different payload producing distinct fact versions and ledgers;
- rejection of an observation timestamp earlier than retained first observed;
- APPEND and FROZEN behavior remaining distinct;
- concurrent same-timestamp idempotency and different-timestamp receipts;
- interruption cleanup and losing-writer validation;
- tampering of every observation manifest identity field, extra/missing keys,
  malformed JSON, unsafe paths, non-UTC timestamps, linked snapshot tampering,
  and supplied observation-ref tampering;
- optional expected-request mismatch;
- input type validation, UTC normalization, stable ordering, and defensive
  immutable return values;
- public exports and absence of credentials or provider/dataframe imports.

## Non-goals and Stop Conditions

Do not:

- change existing snapshot manifest schema, path, identity, or public method
  signatures;
- add source availability fields, endpoint date manifests, RawFact/DerivedFact
  envelopes, dataframe support, or consumer session logic;
- automatically snapshot Tushare client results;
- list unrelated requests or expose a global snapshot inventory;
- add pruning, deletion, overwrite, migration, or remote storage;
- add dependencies, change package versions, edit consumers, commit, push,
  publish, or call live services.

Stop with `EXECUTION_BLOCKED` if the frozen hash changes, backward-compatible
implementation is infeasible, an observation cannot be validated without
trusting caller-supplied identity fields, or pre-existing overlapping edits
cannot be preserved.
